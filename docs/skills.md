# gstack 技能总览

本文按角色和工作流阶段介绍 gstack 的主要技能，帮助你快速理解每个 slash command 该在什么时候用、会产出什么，以及它如何与其他技能衔接。

## 一张图看懂

gstack 把软件开发拆成一条明确链路：

**想清楚问题 → 定方案 → 写代码 → 审代码 → 跑测试 → 发版本 → 做复盘**

不同技能分别接管这条链路中的一个阶段。你不必每次都把所有技能用一遍，但如果你按照这条顺序使用，产出的稳定性会显著更高。

## 1. 想清楚问题

### `/office-hours`

这是最推荐的入口技能。它不是简单地记录你的需求，而是像一次高压版产品讨论：

- 追问真实痛点，而不是停留在功能描述
- 逼你举具体场景，而不是泛泛而谈
- 主动质疑你对问题的 framing
- 给出 2-3 条不同实现路线
- 推荐最小但最有验证价值的切入点

当你说“我想做一个功能”时，`/office-hours` 的职责是判断：这到底是一个功能、一个产品、一个工作流，还是一类更大的系统问题。

**适用场景：**

- 新产品思路还不清晰
- 明明知道哪里痛，但说不清该做什么
- 不确定该先做哪个最小切口

**常见产出：**

- 一个更准确的问题定义
- 更窄的首发版本
- 一份后续计划技能可直接读取的设计文档

## 2. 定方案

### `/plan-ceo-review`

这个技能从“公司和产品负责人”的角度看问题。它会质疑范围、目标和上限，判断你现在提的方案到底是 7 分完成度，还是有机会变成 10 分产品。

它适合在你已经有一份初步方案之后使用，主要回答：

- 这个问题有没有被重新定义的必要
- 方案是不是做小了，或者做偏了
- 哪些部分值得扩张，哪些部分应该砍掉

### `/plan-eng-review`

如果说 `/plan-ceo-review` 是看“你该做什么”，那 `/plan-eng-review` 看的是“你准备怎么把它做对”。

它关注：

- 架构分层
- 数据流
- 状态转移
- 错误处理
- 测试矩阵
- 性能和边界情况

它会把隐藏假设掀出来，让你在写代码前就看清楚风险。

### `/plan-design-review`

这个技能专门审方案里的设计质量。它不会只说“看起来还行”，而是会按多个设计维度打分，并说明一个 10 分设计到底应该是什么样。

它适合：

- 页面、产品或交互设计占比较高的需求
- 已经有草图或设计设想，但没有设计把关
- 想在实现前先避免“AI slop”式的中庸界面

## 3. 构建设计系统

### `/design-consultation`

这是从零搭建设计系统的技能。它不只是“选个字体和主色”，而是会：

- 研究你所在领域的产品和视觉语言
- 提出保守方案与有风险但更有辨识度的方案
- 输出可执行的设计方向
- 将设计系统作为后续实现和评审的依据

适合：

- 新产品起步
- 需要形成统一品牌和交互语言
- 现有界面还没有完整设计系统

## 4. 写代码前后的技术把关

### `/review`

`/review` 面向合并前的代码审查。它重点找的是那些：

- CI 可能不报错
- 本地也不一定容易复现
- 但上线后很容易出大问题

它会特别关注：

- 数据安全
- 并发与竞态
- LLM 输出信任边界
- 条件分支遗漏
- 枚举或状态值没有处理全
- 测试覆盖缺口

### `/investigate`

这是调试技能。它的核心原则非常简单：**不先找根因，就不允许直接修。**

它适合：

- 线上行为异常但原因不明
- 修了几次都没彻底解决的问题
- 涉及数据流、状态流、异步逻辑的复杂 bug

它通常会要求你先完成：

- 现象复述
- 证据收集
- 假设建立
- 验证实验

然后才进入修复阶段。

## 5. 设计与视觉质量

### `/design-review`

如果 `/plan-design-review` 是“实现前审方案”，那 `/design-review` 就是“实现后审成品并直接修”。

它会：

- 检查视觉层级、留白、对齐、颜色、字体、组件一致性
- 抓出典型 AI 生成界面的平庸感
- 用真实页面和截图进行 before / after 对比
- 在必要时直接提交原子修复

适合：

- 已经做完页面，想做一次视觉 QA
- 页面能用，但整体观感“就是不高级”
- 想系统清理视觉不一致和交互粗糙问题

## 6. 真实浏览器测试

### `/browse`

`/browse` 是 gstack 的基础设施技能。它让代理拥有浏览器“眼睛”和“手”：

- 打开真实页面
- 点击、输入、滚动
- 看控制台和网络请求
- 截图和快照
- 对比页面变化

很多上层技能都会依赖它，例如 `/qa`、`/design-review`、`/setup-browser-cookies`。

### `/setup-browser-cookies`

这个技能专门解决登录态测试。它可以从真实浏览器导入 cookie，让无头会话直接继承已有登录状态，避免反复登录或卡在复杂认证流程。

适合：

- 测试后台页面
- 测试需要登录态的用户流程
- 遇到普通自动化难以穿透的认证壁垒

## 7. QA

### `/qa`

`/qa` 是“测试并修复”的闭环技能。它会：

- 用真实浏览器跑关键路径
- 发现问题后直接定位和修复
- 为修复补回归测试
- 再次验证问题是否真的解决

它非常适合 staging 验收或 feature 完成后的系统性检查。

### `/qa-only`

与 `/qa` 相同的方法论，但只出报告，不做修改。适合：

- 你只想要 bug 清单
- 你想把修复留给别的工程师
- 你想先评估质量，再决定是否投入修复

## 8. 发布与文档同步

### `/ship`

`/ship` 是发布技能。它的职责不是单纯 `git push`，而是把“准备上线”这件事变成一个完整流程：

- 同步主分支
- 跑测试
- 做发布前检查
- 推送分支
- 创建 PR

如果项目缺测试基础设施，它还会尽量补足最基本的发布前护栏。

### `/document-release`

很多团队的问题不在于不写文档，而在于文档总是落后于真实代码。这个技能专门解决“发布后文档漂移”：

- 读取项目主要文档
- 对照代码差异
- 更新 README、ARCHITECTURE、CONTRIBUTING、CLAUDE、TODOS 等
- 清理明显过时的描述

它适合在功能合并前后执行一次，让仓库文档始终贴近实际状态。

## 9. 复盘

### `/retro`

`/retro` 面向每周或每个阶段性迭代结束后的复盘。它会从提交历史和工程轨迹中总结：

- 每个人的贡献
- 发货节奏
- 测试健康度
- 最近的改进趋势
- 下一步最值得关注的问题

它的价值不在于生成一份好看的总结，而在于让团队的节奏、质量和习惯变成可讨论的对象。

## 10. 增强工具

### `/codex`

让 OpenAI Codex CLI 从另一个模型视角做代码审查或咨询。适合：

- 需要第二意见
- 想让另一个模型专门挑战你的方案
- 希望获得跨模型交叉视角

### `/careful`

在危险操作前提供安全提醒，例如：

- `rm -rf`
- `DROP TABLE`
- `git push --force`
- `git reset --hard`

### `/freeze`

把修改范围锁定到单个目录，防止代理“顺手”改动无关文件。

### `/guard`

同时启用 `/careful` 和 `/freeze`，适合生产环境或高风险排障。

### `/unfreeze`

解除 `/freeze` 带来的范围限制。

### `/gstack-upgrade`

升级 gstack，并帮助你区分当前是全局安装还是 vendored 到项目内的版本。

## 建议使用顺序

如果你从零开始推进一个功能，推荐顺序是：

1. `/office-hours`
2. `/plan-ceo-review`
3. `/plan-eng-review`
4. `/plan-design-review`（如果这个功能有明显 UI/UX 面）
5. 编码实现
6. `/review`
7. `/qa` 或 `/qa-only`
8. `/document-release`
9. `/ship`
10. `/retro`

当然，不同项目不一定每次都全走一遍。真正重要的是：把这些技能视作不同阶段的把关人，而不是“更多 prompt”。

## 什么时候该用哪个技能

可以用下面这个心智模型快速判断：

- 还没把问题想明白：`/office-hours`
- 方案可能做偏了：`/plan-ceo-review`
- 架构和测试还没锁定：`/plan-eng-review`
- UI 方案还不够成熟：`/plan-design-review`
- 需要完整设计系统：`/design-consultation`
- 想做合并前代码审查：`/review`
- 正在查一个顽固 bug：`/investigate`
- 页面已经做完，想做视觉质量提升：`/design-review`
- 想真实点一遍关键流程：`/qa`
- 只想要 bug 报告：`/qa-only`
- 准备推分支和发 PR：`/ship`
- 文档已经和代码脱节：`/document-release`
- 一周结束，想看团队节奏和改进点：`/retro`

## 最后的建议

gstack 的核心价值不是单个技能有多“聪明”，而是它给了代理清晰角色、明确边界和可衔接的工作流。

如果你只是把它当作一组零散命令使用，它依然有用；但如果你把它当作一支小型虚拟工程团队来组织，收益会大很多。
